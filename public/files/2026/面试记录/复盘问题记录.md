## 技术问题

### 1、React 中事件绑定和 js 中事件绑定的区别？

---

1. 基本写法区别

```js
// 原生 JS：全小写，传字符串
btn.onclick = handleClick;
btn.addEventListener('click', handleClick);
<button onclick="handleClick()">

// React：驼峰命名，传函数（不是字符串），用 JSX
<button onClick={handleClick}>
```

---

2. 核心区别：合成事件（SyntheticEvent）

React 的事件不是原生 DOM 事件，而是 React 自己封装的 SyntheticEvent：

- 跨浏览器兼容（抹平 IE 等差异，现在意义减弱但机制保留）
- API 和原生事件一致：e.preventDefault()、e.stopPropagation()、e.target 等
- 但不能用 return false 阻止默认行为，必须显式调 e.preventDefault()

---

3. 事件委托机制（最重要的区别）

原生 JS： 事件直接绑定在每个 DOM 节点上：

```js
// 100 个按钮就要绑 100 次
document.querySelectorAll("button").forEach((btn) => {
  btn.addEventListener("click", handler);
});
```

React： 事件统一委托到根节点（React 17+ 是 root 容器，React 16 是 document）：

你写的 onClick={fn}
↓ 并没有绑在 button DOM 上
事件统一绑在 #root 上
↓ 事件冒泡到 root 时，React 按虚拟 DOM 树找到对应 handler 执行

好处：

- 减少内存占用，不用给每个节点绑监听器
- 动态新增/删除节点时不用手动绑定/解绑

---

4. 执行时机和冒泡的差异（面试高频坑）

```js
function App() {
  const ref = useRef();

  useEffect(() => {
    // 原生监听：在真实 DOM 上
    ref.current.addEventListener("click", () => {
      console.log("原生事件");
    });
  }, []);

  return (
    <button ref={ref} onClick={() => console.log("React 事件")}>
      点我
    </button>
  );
}
```

点击后输出顺序：

原生事件 ← 目标元素上的原生监听先触发
React 事件 ← 冒泡到 root 容器时才触发

因为 React 17+ 的监听器挂在 root 容器上，原生事件先在目标节点执行，冒泡到 root 后 React 事件才执行。

---

5. e.stopPropagation() 的坑

React 合成事件的 stopPropagation 挡不住外层的原生事件，反之亦然：

```js
document.addEventListener('click', () => console.log('document 原生'));

<div onClick={e => { e.stopPropagation(); console.log('React'); }}>
```

点击后 document 上的原生监听仍然会触发（React 17+ 挂在 root 容器上，stopPropagation 只能阻止 React 合成事件体系内的传播）。

如果必须阻止，用 e.nativeEvent.stopImmediatePropagation()。

---

6. 事件池（Event Pooling）——历史考点

- React 16 及以前：合成事件对象会被复用，异步访问 e 的属性会是 null，需要 e.persist()
- React 17 起已移除事件池，可以直接异步访问，现在面试提一句"知道这个历史机制"即可

```js
// React 16 的坑
onClick={(e) => {
  setTimeout(() => console.log(e.target), 0); // null！需要 e.persist()
}}
```

---

7. Class 组件中的 this 绑定

原生 JS 不存在这个问题，React class 组件需要处理 this：

```js
class App extends React.Component {
  handleClick() {
    console.log(this);
  } // undefined！

  render() {
    return (
      <>
        <button onClick={this.handleClick.bind(this)}>方案1 bind</button>
        <button onClick={() => this.handleClick()}>方案2 箭头函数</button>
        <button onClick={this.handleClick}>方案3 构造函数/类字段</button>
      </>
    );
  }
}
```

函数组件没有这个问题。

### 2、fiber 架构的作用？和以前的区别？为什么不阻塞渲染？

这是 React 16 重写的核心协调引擎（Reconciler）。理解它要抓住一条主线：Fiber 是为「并发」而生的架构——让渲染可以被打断、恢复和优先级调度。

---

一、Fiber 的作用

旧架构（Stack Reconciler）的问题

React 15 及以前，渲染是同步递归、一气呵成的：

// 递归处理整棵组件树，像函数调用栈一样层层往下
ReactDOM.render(<App />)
→ 递归 diff 所有组件
→ 递归创建所有 DOM
→ 全部完成后才归还主线程

问题：

- 组件树一旦很大，这一整套递归可能占用主线程 几十到上百毫秒
- 期间浏览器无法响应输入、动画、点击 → 掉帧、卡顿
- 渲染过程不能中断，递归走到一半无法暂停

Fiber 要解决的问题

1. 把渲染工作拆成小单元，每个单元执行完可以让出主线程
2. 支持优先级调度：紧急更新（输入框输入）优先，非紧急（渲染大列表）延后
3. 支持中断和恢复、复用、丢弃
4. 由此支撑 Concurrent Mode（并发特性）：useTransition、useDeferredValue、Suspense 等

---

二、Fiber 是什么（和以前的本质区别）

Fiber 既是一种数据结构，也是一个工作单元。

1. 数据结构：链表取代递归调用栈

Fiber 把原来的「虚拟 DOM 树 + 递归」改造成 链表结构，每个组件对应一个 Fiber 节点：

type Fiber = {
type, // 组件类型
stateNode, // 对应的 DOM/组件实例
child, // 第一个子节点
sibling, // 右边的兄弟节点
return, // 父节点
alternate, // 另一棵树中对应的 Fiber（双缓存）
effectList, // 副作用链
lanes, // 优先级标记
flags, // 要做的操作（增/删/改）
}

用 child → sibling → return 三个指针把树串成可遍历的链表，这样就不需要递归栈——遍历可以随时暂停在任意节点，下次从该节点继续。这是"可中断"的物理基础。

2. 双缓存（Double Buffering）

内存中同时存在两棵 Fiber 树：

current 树 ← 当前屏幕上显示的
workInProgress 树 (WIP) ← 正在后台构建的
↕ alternate 指针互相对应

更新时在 WIP 树上构建，构建完成后一次性切换 current = WIP。中断/丢弃时直接扔掉 WIP，屏幕上的内容不受影响。

---

三、为什么不阻塞渲染（核心机制）

1. 时间切片（Time Slicing）

Fiber 配合 Scheduler，按 5ms 左右一个时间片执行：

// 伪代码：浏览器空闲时才干活
function workLoop(deadline) {
while (nextUnitOfWork && deadline.timeRemaining() > 1ms) {
nextUnitOfWork = performUnitOfWork(nextUnitOfWork); // 处理一个 Fiber 单元
}
if (nextUnitOfWork) {
// 时间片用完 → 让出主线程，请求下一帧继续
requestIdleCallback(workLoop);
} else {
commitRoot(); // 全部单元处理完 → 提交
}
}

每处理完一个 Fiber 单元就检查：这一帧还有没有剩余时间？ 没有就让出主线程给浏览器绘制/响应事件，下一帧接着干。用户完全感知不到，因为浏览器每 16ms 都有机会刷新画面。

2. 关键区分：render 阶段可中断，commit 阶段不可中断

Fiber 把一次更新明确分成两个阶段：

│ Render（协调阶段） │ 遍历 Fiber、diff、找出所有变更，构建 effectList │ ✅ 可中断、可恢复、可丢弃，纯 JS 计算，不碰真实 DOM │
│ Commit（提交阶段） │ 把所有变更一次性同步写入 DOM、执行 useEffect/useLayoutEffect │ ❌ 不可中断，必须一气呵成（否则用户看到中间态） │

"不阻塞渲染"特指 render 阶段的协调工作被切片；最终改 DOM 的 commit 依然同步，但它只是执行已计算好的变更，速度很快。

3. 优先级调度（Lane 模型）

Fiber 用 Lanes 给更新标记优先级，Scheduler 决定先干谁：

// 高优先级
输入框 onChange、紧急响应
// 低优先级
渲染长列表、复杂计算（可用 startTransition 标记）

高优先级更新到来时，可以中断正在进行的低优先级 render，先处理紧急的，处理完再来（或丢弃旧结果重做）。例子：

const [isPending, startTransition] = useTransition();

// 输入立即响应（紧急），过滤后的大列表渲染被标记为非紧急
setInputValue(value);
startTransition(() => setListFilter(value));

---

面试一句话答法

"Fiber 是 React 16 重写的协调架构。旧的 Stack Reconciler 用递归同步遍历整棵树，组件一大就会长时间占用主线程造成卡顿。Fiber 把虚拟 DOM 改造成链表结构的工作单元，配合 Scheduler 做时间切片——render 阶段每干完一个单元就检查剩余帧时间，可以中断、恢复和按 Lane 优先级调度，让浏览器保持响应；最终 diff 结果在 commit 阶段一次性同步写入 DOM。它的目的就是支撑并发渲染，这也是 useTransition 这类特性的底层基础。"

### 3、你是怎么做性能优化的？

我的核心思路是：**先度量、后优化，按加载、渲染、运行时分层治理，并把性能保障左移到流程中。** 不做"凭感觉"的优化，一切以数据和指标为准。

一、先确立指标：以 Core Web Vitals 为核心

| 指标                        | 含义                     | 目标    |
| --------------------------- | ------------------------ | ------- |
| **LCP**（最大内容绘制）     | 首屏主要内容加载完成时间 | ≤ 2.5s  |
| **INP**（交互到下一次绘制） | 页面整体交互响应性       | ≤ 200ms |
| **CLS**（累计布局偏移）     | 视觉稳定性，避免内容跳动 | ≤ 0.1   |

辅助指标：FCP、TTFB、TBT、资源体积、请求数、长任务数量。

度量工具：

- 实验室：Lighthouse、WebPageTest
- 真实用户：Performance 面板、`web-vitals` 库采集 RUM、埋点上报
- 先区分"实验室数据"和"真实用户数据"，优化以真实瓶颈为依据

---

二、加载阶段优化（首屏速度）

**资源体积：**

- 代码分割：路由级懒加载（`React.lazy` + `Suspense`）
- Tree Shaking、按需引入（lodash、UI 组件库）
- 压缩：Gzip/Brotli，移除未使用代码
- 图片：WebP/AVIF、响应式图片、压缩、`<img loading="lazy">`

**加载策略：**

- 资源优先级：`preload` 关键资源、`prefetch` 下一路由、`dns-prefetch / preconnect`
- 非关键脚本延迟（`defer/async`）
- 利用 HTTP 缓存与 CDN、HTTP/2
- 字体优化：`font-display: swap`，避免 FOIT

**首屏数据：**

- 接口聚合、首屏数据 SSR/SSG、骨架屏降低感知等待

三、渲染阶段优化（避免卡顿与重渲染）

- 合理拆分组件与状态，缩小重渲染范围
- 合理使用 `memo / useMemo / useCallback`，但不滥用（避免优化本身的成本）
- 列表优化：虚拟滚动（react-window）、稳定 key、避免长列表全量渲染
- 避免频繁操作 DOM、避免强制同步布局（layout thrashing）
- 大计算量任务切片或放进 Web Worker，不阻塞主线程
- 使用并发特性：`useTransition / useDeferredValue` 标记非紧急更新

---

四、运行时优化

- 减少不必要的请求与重复渲染（批处理、请求缓存/去重）
- 事件防抖/节流，滚动/resize 监听及时解绑
- 注意内存泄漏：定时器、监听器、订阅在卸载时清理
- 动画优先使用 `transform / opacity`（走合成层），避免触发重排重绘

---

五、CLS 专项（容易被忽略）

- 图片/视频/iframe 预留尺寸（`aspect-ratio`）
- 字体 `display: swap`
- 避免在已有内容上方动态插入元素（广告、弹窗预留位置）

---

六、把性能保障左移（体系化）

- 构建产物分析：`webpack-bundle-analyzer`，设置**性能预算（Performance Budget）**
- CI 中加入 Lighthouse 卡点，超标告警
- 上线后用 RUM 持续监控，而不是优化一次就结束
- 结合 AI：用工具自动识别大体积依赖、给出优化建议并生成优化方案

---

一句话总结

> 我以 Core Web Vitals 为标准，先用工具和真实用户数据定位瓶颈，再分别从加载（拆包、压缩、缓存、懒加载）、渲染（减少重渲染、虚拟列表、并发更新）、运行时（防泄漏、不阻塞主线程）三个层面针对性优化，并通过性能预算和 CI 监控把保障固化到流程里，让性能可持续而不是一次性优化。

---

结合项目可补充的 STAR 案例

- **场景（S）**：项目首屏 LCP 偏高、长列表滑动卡顿
- **任务（T）**：将 LCP 降到 2.5s 内、消除明显卡顿
- **行动（A）**：
  - 路由懒加载 + 按需引入 + Brotli，首屏体积下降 X%
  - 关键接口/字体 preload，图片全部改 WebP 懒加载
  - 长列表接入虚拟滚动，重计算移入 Web Worker
- **结果（R）**：LCP 从 X s 降到 Y s，CLS < 0.1，交互响应明显改善

### 4、请你设计一个前端文件预览组件？

一、先明确需求与边界

我会先和面试官对齐几个关键问题，而不是直接写代码：

1. **支持哪些文件类型**：图片、PDF、文本、视频、音频、Office 文档？
2. **文件来源**：本地文件（拖拽/上传，File/Blob）还是远程 URL？文件大小范围？
3. **运行环境**：PC 还是移动端？是否需要兼容 IE/旧浏览器？
4. **核心交互**：是否需要缩放、旋转、翻页、全屏、下载？
5. **是否有数量要求**：单文件预览，还是多文件列表/切换？

---

二、总体设计思路

采用 **「统一外壳 + 插件化渲染器（Registry + 策略模式）」**：

- 外层 `Preview` 组件负责：文件获取、类型识别、加载/错误态、通用工具栏
- 内层按文件类型分发到不同的 `Renderer`（ImageViewer / PdfViewer / CodeViewer ...）
- 新增类型只需"注册一个渲染器"，不修改主组件——符合开闭原则

```
<Preview file={url | File} />
    │
    ├─ 1. 获取文件 / 读取元信息
    ├─ 2. 识别类型（ext + MIME + 魔数兜底）
    ├─ 3. 匹配对应的 Renderer
    ├─ 4. 渲染（loading / error / empty 兜底）
    └─ 通用工具栏：缩放、旋转、下载、全屏
```

---

三、各类型的预览方案

| 类型       | 格式                 | 技术方案                                                                       |
| ---------- | -------------------- | ------------------------------------------------------------------------------ |
| 图片       | png/jpg/gif/webp/svg | 原生 `<img>`；缩放旋转用 CSS transform；大图可 canvas                          |
| PDF        | pdf                  | `pdf.js` / `react-pdf` 按页渲染到 canvas，支持翻页、缩放                       |
| 文本/代码  | txt/json/md/log      | `FileReader`/`fetch` 读取，代码用 `highlight.js`/`Prism` 高亮，Markdown 可渲染 |
| 视频       | mp4/webm             | 原生 `<video controls>`，支持清晰度/流式播放                                   |
| 音频       | mp3/wav              | 原生 `<audio>`                                                                 |
| Office     | doc/xls/ppt          | 前端不直接解析：用 **微软 Office Online iframe** 或后端转 PDF/图片后预览       |
| 不支持类型 | 其他                 | 降级卡片：显示文件信息 + 下载按钮                                              |

> 设计原则：**能用浏览器原生能力的就不引重型库；复杂格式（Office）优先服务端转换，避免前端包体积膨胀。**

---

四、关键模块设计

1.  类型识别（不能只信扩展名）

```ts
// 优先级：MIME → 扩展名 → 文件头魔数（magic number）
function detectType(file: File): FileType {
  // file.type 可能被篡改或缺失，扩展名也可伪造
  // 必要时读取前几个字节判断真实类型（PNG: 89 50 4E 47，PDF: %PDF）
}
```

2. 渲染器注册（插件化核心）

```ts
type Renderer<T = unknown> = {
  type: FileType;
  component: React.ComponentType<ViewerProps<T>>;
  match: (meta: FileMeta) => boolean;
};

const registry = new Map<FileType, Renderer>();
export function registerRenderer(r: Renderer) {
  registry.set(r.type, r);
}

function Preview({ file }: { file: string | File }) {
  const meta = useFileMeta(file);
  const renderer = registry.get(meta.type);
  if (meta.loading) return <Loading />;
  if (meta.error) return <ErrorState />;
  if (!renderer) return <UnsupportedFile meta={meta} />;
  return <renderer.component meta={meta} />;
}
```

3.  大文件处理

- 图片/PDF 大图：懒加载、分片、按需渲染当前页，避免一次性加载
- 文本：截断或虚拟滚动，防止超大文本撑爆内存
- 远程文件：优先用 URL 直链，必要时用 Blob URL + 及时 `revokeObjectURL` 释放
- 设文件大小上限，超限提示下载而非预览

---

五、安全设计（重点，容易加分）

预览组件常处理不可信文件，必须考虑：

1. **XSS 防护**：
   - SVG 可内嵌 `<script>`，建议沙箱化或转成图片处理，不直接 `innerHTML`
   - Markdown 渲染要做转义，禁用原始 HTML 或用 DOMPurify 清洗
2. **下载内容用 Blob 处理**，避免执行型文件直接在当前环境打开
3. **iframe 预览加沙箱**：`sandbox` 属性，限制脚本和跳转
4. 校验文件真实类型，防止把恶意文件伪装成图片

---

六、性能与体验

- 按需加载重型依赖：`pdf.js`、代码高亮通过 `React.lazy` 动态引入，不进主包
- 统一的 loading / error / empty / 不支持 四种兜底态
- 工具栏支持：缩放、旋转、翻页、全屏、下载（不同类型只展示可用项）
- 支持键盘快捷键（Esc 关闭、方向键翻页）
- 移动端：手势缩放、自适应屏幕

---

七、对外 API 设计

```tsx
<Preview
  file={urlOrFile} // 远程 URL 或本地 File
  name="report.pdf" // 文件名（辅助识别）
  size={102400} // 大小
  zoomable // 是否允许缩放
  downloadable
  onClose={fn}
  onError={fn}
/>
```

设计要点：**受控与非受控结合、props 精简、复杂能力通过配置项开关**，并保证渲染器可独立注册扩展。

八、回答亮点总结

1. 先对齐需求，不盲目设计
2. 外壳 + 插件化 Renderer，类型扩展开闭原则
3. 类型识别用 MIME + 扩展名 + 魔数多重校验
4. 重点考虑安全（XSS/沙箱/DOMPurify）和大文件性能（懒加载、动态 import）
5. 完善的兜底态和降级方案（不支持就下载、Office 走服务端转换）

### 5、谈谈你对 skills 和 mcp 的理解？

---

一、MCP：连接模型与外部世界的「标准协议」

MCP（Model Context Protocol） 是 Anthropic 提出的开放协议，解决的核心问题是：每个工具/数据源都要单独对接一次，N 个模型 × M 个工具 = N×M 的集成成本。

它就像 AI 应用的 「USB-C 接口」——统一了模型与外部系统的连接方式：

AI 应用（MCP Host/Client）
↕ 标准协议
MCP Server 暴露三类能力：

- Tools（工具）：可执行的函数/操作，如发请求、操作浏览器、写数据库
- Resources（资源）：可读取的数据，如文件、记录
- Prompts（提示模板）：预设的交互模板

要点：

- 两种传输方式：stdio（本地子进程，适合本地工具）和 SSE/Streamable HTTP（远程服务）
- 一次对接，处处可用：同一个 MCP Server，Claude Desktop、Cursor、Coze Studio 等任何支持 MCP 的客户端都能接入
- 典型场景：浏览器自动化（Playwright MCP）、文件系统、数据库查询、内部系统对接

二、Skills：打包「知识与工作方法」的扩展机制

Skills 解决的是另一个问题：模型不知道「在特定场景下该怎么做」的专门知识和流程。

一个 Skill 的本质是一个目录，核心是 SKILL.md：

---

name: english-proofreading
description: 触发条件描述（模型据此判断何时启用）

---

# 具体的指令、规范、工作流程、示例

- 输出格式
- 操作步骤
- 参考资料引用

关键机制：

1. 声明式触发：模型根据 description 自动判断当前任务是否需要该 Skill——不是每次都加载
2. 渐进式披露（Progressive Disclosure）：平时只加载 name + description（省 token），触发后才读取完整正文，复杂 Skill 还可拆分多个文件按需读取
3. 打包的是「know-how」：领域知识、SOP、输出规范、示例——教模型「怎么做一件事」
4. Skill 里可以声明并调用 MCP 工具

---

"MCP 是连接模型和外部工具/数据的标准协议，类似 AI 界的 USB-C，通过 Tools、Resources、Prompts 三种原语把外部能力标准化，一次对接处处可用；Skills 是打包专门知识和工作流程的机制，核心是带触发描述的 SKILL.md，靠渐进式披露按需加载，解决'模型在特定场景下该怎么做'的问题。区别是：MCP 给的是运行时的执行能力，Skills 给的是上下文里的知识规范。两者组合使用——Skill 指导行为，MCP 完成真实操作，共同支撑一个专业 Agent。"

### 6、你是怎么进行 CR 的？

CR 的首要目的不是挑 bug，而是「共同对代码质量负责 + 知识在团队内流动」。

- 工具能发现的（格式、lint、类型、单测覆盖）交给工具，人的注意力放在机器判断不了的地方
- Review 的是代码不是作者，评论用「建议/疑问」语气，不追求说服，追求最优解
- MR 要小——超过 400 行的 Review 基本是走过场，我会推动拆分

"我把 CR 看作团队共同对质量负责，而不是走流程。方法上：先理解需求和整体方案，再按正确性、安全、设计、性能、可维护性分层看，风格类问题全部交给 ESLint、Prettier、CI 去拦。前端我会重点关注 Hooks 依赖、副作用、异步状态和类型安全。同时我会做质量左移，并用 AI 做第一遍 Review 和把团队规范固化成规则甚至 Skill，让人聚焦在架构判断上，但 AI 的建议一定人工核实。作为作者我也会把 MR 拆小、描述写清楚，降低别人的 Review 成本。"

### 7、你是怎么借助 AI 进行开发的？

---

一、我的核心认知

▎ AI 不是"帮我写代码"的工具，而是贯穿研发全流程的"协作搭档"。越是高杠杆、重复性、探索性的工作越适合交给它；而架构决策、业务语义、最终验收必须自己把关。

我把它定位成：资深结对程序员 + 不知疲倦的助手，但责任始终在我。

---

二、按研发全流程使用

│ 需求理解 │ 让它帮我拆解需求、列出边界 case 和潜在风险、生成技术方案的 Checklist，作为思考的"第二大脑" │
│ 方案设计 │ 让它给出多种实现方案和取舍，我来做决策——它扩展选项空间，我负责拍板 │
│ 编码实现 │ 样板代码、CRUD、类型定义、单测用例让它生成；复杂逻辑我写主干，让它补全和重构 │
│ 写测试 │ 根据实现生成边界/异常用例，补充我容易漏掉的 case，再由我判断测试是否有效（而非"为了覆盖率"） │
│ 调试排错 │ 贴报错和上下文让它帮忙定位假设、解释堆栈；但我会用实际运行去验证，不轻信 │
│ CR │ AI 先做第一遍 Review，指出明显问题和测试缺口（上一题已展开） │
│ 文档/重构 │ 生成提交信息、接口文档、解释陌生代码、跨文件重命名和重构 │

典型场景：接手陌生模块时，我会让 AI 先通读代码、画出调用关系和数据流，快速建立全局认知——这比自己逐行读快数倍。

---

三、工程化建设：不只是自己用，而是让团队用好

这是我和普通使用者最大的区别——我会建设团队的 AI 研发体系：

1. 上下文优化：AI 写得好不好，关键在上下文。我会整理项目规范、架构约定、代码风格，沉淀成 CLAUDE.md / Rules / Skills，让 AI 在生成阶段就符合团队标准，而不是写完再返工
2. 能力扩展：通过 MCP Server 让 AI 接入内部系统、数据库、浏览器自动化、部署平台等真实工具，把它从"只会写代码"扩展到"能执行完整任务"
3. 流程固化：把高频操作（发版、建分支、生成报告）做成 Skill / 工作流，统一团队用法
4. 推广与度量：制定使用规范、组织分享，并用效率指标衡量效果——我过往推动的 AI Coding 流程优化，整体研发效率提升约 30%

---

四、我的使用方法论（保证质量的关键）

1. 小步验证：让 AI 产出一小块就运行、验证，不堆积一大段无法排查的代码
2. 给好上下文：清晰描述目标、约束、输入输出，提供相关代码——"垃圾进垃圾出"，AI 的质量取决于我的提问
3. 保持批判性：AI 会"自信地犯错"，尤其在边界条件、API 幻觉、业务语义上，每一处我都读得懂、验得过才合并
4. 复杂问题拆细：模糊的大任务先一起拆解，再分步执行，降低出错率
5. 核心部分自己掌控：架构设计、安全相关、涉及资金/隐私的逻辑，不盲交出去

五、人机边界：什么交给 AI，什么必须自己来

│ ✅ 适合交给 AI │ ⚠️ 必须自己把关 │
│ 样板/重复代码、补全 │ 架构与技术选型 │
│ 单测、文档、注释 │ 业务语义和需求正确性 │
│ 代码解释、方案选项 │ 安全、权限、敏感数据 │
│ 重命名、机械重构 │ 最终验收和线上责任 │

"我把 AI 当作贯穿研发全流程的协作搭档，而不只是代码补全：需求阶段让它帮我拆解和列边界 case，设计阶段让它给多种方案我来决策，编码阶段把样板代码、类型、单测交给它，调试和 CR 也用它先做第一遍。但我坚持小步验证、保持批判，架构决策、业务语义和最终验收一定自己把关。
更重要的是我会做工程化建设：通过优化上下文、把团队规范沉淀成 Rules 和 Skills、用 MCP 让 AI 接入内部系统和真实工具、把高频流程固化下来，让整个团队而不只是我个人用好。"
